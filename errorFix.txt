ERROR 1: `npm ci` fails inside Docker - "Missing: <pkg> from lock file"
----------------------------------------------------------------------
SYMPTOM:
  npm ci failed with dozens of lines like:
    npm ERR! Missing: jest@^29.7.0 from lock file
    npm ERR! Missing: ts-jest@^29.1.0 from lock file
  caused the docker build to abort at the `npm install`/`npm ci` step.

ROOT CAUSE:
  Dependencies (jest, ts-jest, @types/jest) were added to package.json
  but package-lock.json was never regenerated, so the lockfile was out
  of sync. `npm ci` requires the lockfile to exactly match package.json.

FIX:
  Run `npm install` at the repo root to regenerate package-lock.json:
    cd my-turborepo
    npm install
  This re-syncs the lockfile with package.json. Also created a
  .dockerignore so node_modules, dist, .env etc. are not copied into the
  Docker build context (keeps the context small and avoids stale state).

ERROR 2: TS1259 - Module 'winston' can only be default-imported
          using 'esModuleInterop'
----------------------------------------------------------------------
SYMPTOM:
  During the TypeScript build stage of the Docker image:
    error TS1259: Module '"/app/packages/shared-logger/node_modules/winston"'
    can only be default-imported using the 'esModuleInterop' flag.

ROOT CAUSE:
  Every package and app tsconfig extended the root `../../tsconfig.json`,
  which is a SOLUTION-STYLE file (only `files: []`, `references`, and
  compiler options that DO NOT include `esModuleInterop`). The real shared
  compiler options live in `tsconfig.base.json`, which has
  `esModuleInterop: true`.

FIX:
  Changed every package/app tsconfig to extend the correct base:
    "extends": "../../tsconfig.base.json"
  Files updated:
    packages/shared-db/tsconfig.json
    packages/shared-kafka/tsconfig.json
    packages/shared-logger/tsconfig.json
    packages/shared-metrics/tsconfig.json
    packages/shared-redis/tsconfig.json
    packages/shared-utils/tsconfig.json
    apps/api-gateway/tsconfig.json        (file was also missing - created)
    apps/delivery-service/tsconfig.json
    apps/event-ingestor/tsconfig.json
    apps/event-router/tsconfig.json
    apps/ws-gateway/tsconfig.json

ERROR 3: api-gateway compile errors (TS2349 / TS7006 / TS1259)
----------------------------------------------------------------------
SYMPTOM:
  `import * as express` / `import * as cors` broke the compile once
  esModuleInterop was enabled, with errors like:
    error TS2349: This expression is not callable
    error TS1259: Module can only be default-imported using esModuleInterop

ROOT CAUSE:
  With `esModuleInterop` enabled, namespace imports (`import * as x`)
  are not callable for CommonJS modules like express/cors.

FIX:
  Changed to default imports in apps/api-gateway/src/index.ts:
    import express from 'express';   // was: import * as express
    import cors from 'cors';         // was: import * as cors

  resolving `helmet` (TS1479 or module resolution error), because

ERROR 6: ioredis crashes the process - "Unhandled error event
          [ECONNREFUSED]" / "MaxRetriesPerRequestError"
----------------------------------------------------------------------
SYMPTOM:
  ws-gateway / event-router / delivery-service crashed on startup with:
    [ioredis] Unhandled error event: AggregateError [ECONNREFUSED]
    MaxRetriesPerRequestError: Reached the max retries per request limit

ROOT CAUSE (two bugs):
  1. packages/shared-redis/src/client.ts created `new Redis(url)` with no
     `.on('error')` handler. When the connection is refused (e.g. Redis
     not ready yet), ioredis emits an 'error' event; with no listener the
     Node process crashes. ioredis would otherwise auto-reconnect.
  2. presence.ts / rateLimit.ts / pubsub.ts call `getRedisClient()` with
     NO url argument, so the fallback `redis://localhost:6379` was used.
     Inside a container `localhost` is the container itself -> refused.
     ws-gateway/connection.ts passed env.REDIS_URL explicitly, so only the
     shared modules were affected.

FIX:
  packages/shared-redis/src/client.ts now:
    - uses process.env.REDIS_URL as the fallback url,
    - attaches `redisClient.on('error', ...)` (suppresses the unhandled
      event so ioredis keeps retrying),
    - sets maxRetriesPerRequest: null and a retryStrategy so `ping()`
      waits for Redis instead of throwing.

ERROR 7: App services crash-loop because Kafka/Redis aren't ready yet
          (startup race) and have no restart policy
----------------------------------------------------------------------
SYMPTOM:
  event-ingestor / event-router / delivery-service exited on first start
  with `ECONNREFUSED ... :29092` because Kafka takes 30-60s to become
  ready (group coordinator / topic leader not available yet).

ROOT CAUSE:
  `await producer.connect()` / `consumer.connect()` run once at startup
  with no retry, and the compose services had no restart policy, so a
  transient startup failure left them permanently down.

FIX:
  1. Added retry loops in each service around the Kafka connect:
       apps/event-ingestor/src/index.ts
       apps/event-router/src/index.ts
       apps/delivery-service/src/index.ts
     (retry every 5s until Kafka is reachable).
  2. Added `restart: unless-stopped` to every service in
     infra/docker/docker-compose.yml so any transient failure self-heals.

ERROR 8: Docker services can't reach each other - "localhost" in .env
----------------------------------------------------------------------
SYMPTOM:
  Containers started but couldn't connect to Mongo/Redis/Kafka because
  the .env file (used for local `npm run dev`) points at localhost.

ROOT CAUSE:
  Inside a container, `localhost` refers to the container itself, not the
  host machine. So MONGODB_URI / REDIS_URL / KAFKA_BROKERS from .env were
  unreachable from the Docker services.

FIX:
  Added per-service `environment:` overrides in docker-compose.yml so the
  containers use the compose service hostnames, while .env keeps its
  localhost values for local development:
    api-gateway:      MONGODB_URI=...@mongo:27017/...
    event-ingestor:   KAFKA_BROKERS=kafka:29092
    event-router:     MONGODB_URI=...@mongo, REDIS_URL=redis://redis:6379,
                      KAFKA_BROKERS=kafka:29092
    delivery-service: same as event-router
    ws-gateway:       REDIS_URL=redis://redis:6379
  (Kafka uses kafka:29092 because 29092 is the container-internal
  listener; localhost:9092 is only for host access.)

ERROR 9: BullMQ needs a dedicated IORedis connection per Queue/Worker
----------------------------------------------------------------------
SYMPTOM:
  After wiring up BullMQ, TypeScript failed to compile delivery-service
  (Cannot find name 'queueConnection') and, at runtime, sharing a single
  Redis connection between a Queue and Worker is unreliable in BullMQ v5.

ROOT CAUSE:
  The original plan used one shared `queueConnection`. BullMQ requires its
  own connection instance per Queue and per Worker (dedicated IORedis), so
  a single shared connection is not usable for both.

FIX:
  Refactored apps/delivery-service/src/queue/deliveryQueue.ts to export a
  `createQueueConnection()` factory (one IORedis per caller, tracked for
  clean shutdown via closeQueues()). deliveryWorker.ts and dlqWorker.ts now
  call `connection: createQueueConnection()`.

ERROR 10: BullMQ v5 has no 'retrying' event; 'failed' fires on EVERY attempt
----------------------------------------------------------------------
SYMPTOM:
  Trying to listen for a `retrying` event to mark notifications RETRYING
  failed — the event does not exist in bullmq 5.80.9. The 'failed' event
  fires on every failed attempt, so a naive handler would move the job to
  the DLQ after the very first failure.

ROOT CAUSE:
  BullMQ v5 emits `failed` per attempt; there is no separate retry event.

FIX:
  In deliveryWorker.ts, branch inside the 'failed' handler on
  `job.attemptsMade >= (job.opts.attempts || 1)`:
  - final attempt  -> add job to the DLQ queue + mark notification FAILED
  - earlier attempt -> mark notification RETRYING (job auto-retries with
    exponential backoff)
  Queue config: 4 attempts, backoff { type: 'exponential', delay: 5000 },
  jobId = eventId (idempotent enqueue).
